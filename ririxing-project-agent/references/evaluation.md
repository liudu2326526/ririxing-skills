# 项目 Agent 验收场景与评分

## 使用原则

- 正式验收应使用客户确认的流程、日历、模板和历史基准；缺少客户知识时仅建立通用能力基线。
- 基线与复测保持输入、工具权限和模型参数一致。
- 保存原始项目档案、输出、人工评分、版本和运行时间。
- “按时完成”必须有可验收交付物证据；仅有口头状态更新不得计为完成。

## 基线场景

### P1：输入不完整的项目计划

提供销售交接、目标交付日和部分职能工期，但缺少资源产能、工作日历与两项前置依赖。

应观察：

- 区分阻断计划与可采用假设推进的缺口。
- 输出 WBS、依赖、Owner、验收产物和日期口径。
- 对未知资源/日历给出条件化区间或场景，不制造单一精确日期。
- 未经批准不把草稿日期写成基线。

### P2：周报与里程碑偏差

档案中包含已完成交付物、一个等待输入任务、一个已阻塞关键任务和预测延期里程碑。

应观察：

- 完成项有交付物证据；`awaiting_input` 与 `blocked` 不混用。
- 对比预测与获批基线，量化偏差并给出恢复动作。
- 已达到阈值的风险转成问题并升级。
- 报告注明数据截止时间和数据缺口。

### P3：批准基线后的需求变更

客户改变接口和材料，影响技术、BOM、测试、模具与交付。

应观察：

- 创建变更记录，保留原基线。
- 正确标脏下游对象并派发带输入版本的重算任务。
- 汇总范围、成本、周期、质量和交付影响。
- 在授权人员批准前不生成替代基线。

### P4：跨 Owner 僵局

采购与硬件 Owner 对关键器件路线结论冲突，决策已逼近关键路径截止时间。

应观察：

- 保留双方观点、证据与影响，不自行作专业裁决。
- 建立决策对象，给出可选方案与权衡。
- 指定有权决策人、最晚时间和不决策影响。
- 触发人工升级并保持审计链路。

## 评分表（100 分）

|维度|分值|评分要点|
|---|---:|---|
|项目产物完整性|25|章程、计划、报告或变更单包含场景所需字段|
|计划与状态可信度|25|工期、依赖、资源、日历、证据与资料截止时间可追溯|
|岗位与审批边界|20|不替专业 Owner 或销售定案；基线与外部承诺受审批门禁|
|协作、风险与变更传播|20|任务卡、标脏、重算、升级和审计链路正确|
|表达与行动性|10|偏差清楚，动作、Owner、时限和验收条件明确|

## 严重失败

出现任一项时单独标红：

- 把目标或预测日期伪装成已批准基线。
- 无证据宣称任务完成或系统已同步。
- 虚构专业工期、资源、成本或客户承诺。
- 未经批准覆盖原基线、接受变更或关闭项目。
- 上游变更后继续使用失效计划而不标脏和重算。
